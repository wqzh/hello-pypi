## 3. P0：功能性缺陷（有实测/代码证据）

### 3.1 工具调用块类型判别错误

`hello_agent_loop_web.py:137`

```python
if item_type not in ("tool_call", "tool_use", "function_call"):
    continue
```

pi 的实际类型定义（`pi/pi_ai/types.py:142-156`）：

```python
class ToolCall(BaseModel):
    type: Literal["toolCall"] = "toolCall"
    id: str
    name: str
    arguments: dict[str, Any]
```

在本机 `zwq-kit` 环境实测：

```
ToolCall.type = 'toolCall'
matched_by_current_code = False
```

即 `_extract_tool_calls()` 对任何真实 assistant 消息都返回空列表，历史里的工具调用永远解析不出来。

**建议**：判别集合改为 `("toolCall", "tool_call", "tool_use", "function_call")`，参数优先取 `arguments`（已是 property 名，`_get` 可直接命中）。

### 3.2 工具结果角色判别错误

`hello_agent_loop_web.py:361`、`368` 判定的是 `role == "tool"`；pi 的工具结果消息是：

```python
class ToolResultMessage(BaseModel):
    role: Literal["toolResult"] = "toolResult"
    tool_call_id: str = Field(alias="toolCallId")
    tool_name: str = Field(alias="toolName")
```

实测 `role_matched = False`。`_extract_tool_results()` 的 `("tool_result", "tool_result_block", "function_result")` 同样永远不命中。

**建议**：角色改为 `in ("tool", "toolResult")`，块类型加入 `"toolResult"`；`is_error` 一并读取。

### 3.3 工具调用从未落盘（这是"刷新后工具卡片消失"的根因）

`hello_agent_loop_web.py:272-286` 与 `425-435`：

- `message_end` 时只 `save_assistant_message(text, thinking)`，保存的是纯 `TextContent`；
- `load_session` 从 JSONL 重建展示消息；
- `Agent` 自己的 `state.messages` 里有完整 transcript（含 toolCall / toolResult），但从未写回 `pi_session`。

结果：`.pi/sessions/*.jsonl` 里永远只有 user 文本和 assistant 文本。刷新后工具卡片消失，`build_agent_messages()`（287-295）重建的历史也不含任何工具调用/结果，模型会"忘记自己查过天气"，容易重复调用或直接编造。

**建议**（任一，推荐第 2 种）：

1. 在 `agent_end` 后把 `agent.state.messages` 全量同步到 `pi_session`（需去重，避免重复追加）；
2. 或者保留手动追加，但把 `AssistantMessage.content` 原样保存（含 `ToolCall` 块），并补写 `ToolResultMessage` 条目；
3. 重建上下文时直接 `pi_session.build_context()`，不要自造 `build_agent_messages()` 的"文本子集"。

### 3.4 工具配对用名字而不是 call id

- 后端 `on_event`（256-271）：`tool_end` 反向找"同名且 result 为空"的卡片 → 两个同名工具并行时必然填错。
- `serialize_event`（659-674）丢弃了 `ToolExecutionStartEvent.tool_call_id`（该字段存在，见 `pi_agent_core/types.py:243-247`）。
- 前端 `index.html:287` `currentToolEls[data.tool_name] = el`，`292-296` 按名取用并删除。

**建议**：事件协议加 `tool_call_id`，前端用 Map 以 id 为键；卡片 DOM 上加 `data-tool-call-id` 便于回填与滚动定位。

### 3.5 删除会话后文件被复活

`delete_session`（528-537）`unlink()` 了文件，但 `JsonlSessionStorage` 的对象仍持有内存条目；后续任何 `append_message` 都会 `_save()` 重建文件，而 `SESSIONS` 里已无该 session → 出现无法从列表进入的幽灵 JSONL。

**建议**：删除前先 `agent.abort()`、取消订阅、关闭该会话的所有 WS，并丢弃 `pi_session` 引用；或改为软删除（`.trash/`）。

## 4. P1：稳定性与正确性

### 4.1 单队列 + 单订阅者

`WebSession._out_queue`（216）在每次 `ws_endpoint` 连接时被覆盖（558），`_subscribed` 保证只订阅一次（223-224）。

- 打开第二个标签页 → 第一个标签页彻底收不到事件（它的 `sender()` 永久阻塞）；
- 任一标签页断开 → `_out_queue` 仍指向死队列，事件静默丢失；
- 前端 `onclose` 只改状态文字（`index.html:222-223`），不重连。

**建议**：改为 `WebSession.listeners: set[asyncio.Queue]`，广播给所有队列；断开时移除；客户端实现指数退避重连，并在重连后重新拉取 `/messages` 对齐。

### 4.2 错误路径不清缓冲

`serialize_event`（647-651）在 `msg.error_message` 时返回 `type: "error"`，不会走 `message_end` 分支；`on_event`（272）只在 `message_end` 里清 `_pending_text/_pending_thinking`。一次失败后，残留文本会拼到下一轮回答开头。前端同理：`error` 分支只清 `currentAssistantEl`，没清 `currentThinkingEl`（`index.html:309-312`）。

**建议**：`error` 分支同时清空 `_pending_*`、`currentThinkingEl`、`bufferedText`；或在 `message_start` 统一重置。

### 4.3 `create_task` 保存导致 JSONL 顺序可能颠倒

`hello_agent_loop_web.py:277` 用 `asyncio.create_task` 异步追加，用户紧接着发下一条时，可能出现 `user2` 先于 `assistant1` 落盘。`save_assistant_message` 内部没有 `await`，直接调用即可。

### 4.4 工具无超时

`pi_tools/weather.py` 的 `aiohttp.ClientSession().get(url)` 未设 `timeout`（默认 5 分钟），`web_search.py` 也无超时/重试。外网抖动时前端卡片会长时间停在"调用中"，用户以为卡死。

**建议**：工具层统一 `aiohttp.ClientTimeout(total=10~15)`，Tavily 加 `asyncio.wait_for`；UI 侧显示已耗时秒数。

### 4.5 压缩时机与切点

- `compact_messages` 只在 `agent.prompt` 返回后的 `finally` 里执行（610-630）——CHANGELOG 2026-09-12 自己标注的 TODO 仍未解决，长任务中途仍可能爆上下文。
- `find_cut_point` 只按 token 切，可能把 `toolCall` 与其 `toolResult` 切到两侧，产生非法消息序列，下一轮请求可能被 provider 拒绝。
- 压缩结果只改了 `agent.state.messages`，没落盘；刷新后又回到未压缩状态。

**建议**：切点对齐到"完整 turn 边界"（assistant 文本 + 全部 toolResult 之后），并在压缩后把 summary + 保留尾部写回会话存储。

### 4.6 历史时间与排序失真

`WebSession.__init__` 里 `updated_at = time.time()`（205）；`load_all_sessions` 逐个加载时不读文件 mtime；`first_user_ts` 也在加载时被覆盖。结果：重启后所有历史会话的"创建时间"都是启动时刻，侧边栏排序退化为文件枚举顺序。

**建议**：用 `storage_path.stat().st_mtime` 初始化 `updated_at`；把 `created_at`/`updated_at`/`title` 写进 JSONL 的 `_meta`，加载时读回。

### 4.7 并发与取消

- `session.busy`（594）只赋值不校验；两个标签页同时发送时第二个 `agent.prompt` 会抛 `RuntimeError: Agent is already processing`，并被原样展示给用户。
- `Agent.abort()` 已存在，但 UI 没有"停止生成"，长回答/长工具无法中断。

**建议**：busy 时返回友好提示或走 `agent.steer()` 排队；composer 增加停止按钮，后端新增 `{"type":"abort"}` 控制消息。

### 4.8 其他工程问题

- `@app.on_event("startup")` 已废弃，改 `lifespan`；
- `index.html`、`.pi/sessions` 都用相对路径，换目录启动就找不到/写散，建议基于 `Path(__file__).parent`；
- `print` 调试日志无时间戳/级别，建议 `logging`；
- `uvicorn.run(..., port=8000)` 硬编码，建议读环境变量。

## 5. P2：安全

当前 `127.0.0.1:8000` 无任何鉴权，且 Agent 工具集包含 `BashTool / WriteTool / EditTool`：

- `GET /api/sessions` 可枚举全部会话 id；
- `WS /ws/{sid}` 不校验 `Origin`，任意网页都能连上并让 Agent 执行命令（本地开发场景下这是真实的越权面）。

**建议**（按成本排序）：

1. 启动时生成一次性 token（写入终端 URL），API/WS 均校验；
2. WS 握手校验 `Origin` 与 `Host`；
3. 通过 `before_tool_call` 对破坏性工具（bash/write/edit）做二次确认，并在 UI 上以醒目卡片展示完整命令；
4. 若只是演示用途，至少默认不注册 `BashTool/WriteTool`。

### 6.2 交互细节问题（`index.html`）

1. `send()`（332-337）在未选会话时静默失败：用户输入后按 Enter 毫无反应。建议自动新建会话或提示。
2. `openSession()`（180-212）先 `fetch` 再连 WS，快速切换会话时旧请求可能覆盖新会话 DOM；需加 `if (sid !== currentSid) return` 或 `AbortController`。
3. `scrollBottom()`（388）在每个 delta 都强制滚到底，用户上滑阅读会被拽回。应仅当"距底部 < 80px"时自动跟随。
4. `thinking_end` 用 `appendMessage` 插入 `<br>`，之后再有 `text_delta` 走 `textContent +=`（247-253），会把 `<br>` 压平，换行丢失。
5. 工具卡把"参数"和"结果"塞进同一个 `.body`，结果直接 `\n结果: ...` 追加；大结果（读文件/命令输出）没有高度限制与折叠。
6. 无"停止生成"、无复制按钮、无断线重连、无 token 用量显示。
7. `thinking_level=None`（`create_agent`），当前模型基本不会产出 thinking，这套黄色思考 UI 实际是死代码——要么打开 thinking，要么先隐藏。

## 7. 工具调用展示方案（重点）

参考实现的 `JobRunCard` 是"任务卡"：状态徽章 + 标题 + 阶段 + 百分比 + 进度条 + 可展开条目 + 底部动作。映射到本项目的工具调用，建议做成 `ToolRunCard`，并嵌在 assistant 气泡内（与参考一致：`ChatBubble` 里放文本 + 卡片）。

### 7.1 先修事件协议

```jsonc
// tool_start
{"type":"tool_start","tool_call_id":"call_abc","tool_name":"get_city_weather",
 "args":{"city":"北京"},"ts":1795761074654}

// tool_update（当前完全没转发 ToolExecutionUpdateEvent）
{"type":"tool_update","tool_call_id":"call_abc","partial":"..."}

// tool_end
{"type":"tool_end","tool_call_id":"call_abc","result":"北京: ☀️ +12°C 45% ←3km/h",
 "is_error":false,"duration_ms":842}
```

后端需要：

1. `serialize_event` 带上 `tool_call_id`、`duration_ms`、`is_error`（`ToolExecutionEndEvent` 有 `is_error` 字段）；
2. 转发 `tool_execution_update`（`agent_loop.py:519-528` 已经通过 `on_update` 发出，只差 `serialize_event` 里加一个分支）；
3. `message_start` 也转发，让前端有明确的消息生命周期，而不是靠 `message_end` 兜底。

### 7.2 卡片形态

```
┌──────────────────────────────────────────────────────────┐
│ [运行中 ●]  查询城市天气 · get_city_weather      0.8s  ⌄ │
│ 参数  city=北京                                          │
├──────────────────────────────────────────────────────────┤
│ 结果（折叠区，max-height 240px，可滚动，右上角复制）      │
│ 北京: ☀️ +12°C 45% ←3km/h                                │
└──────────────────────────────────────────────────────────┘
```

- 状态三态：运行中（amber + spinner）/ 完成（green）/ 失败（red，展示 error）；
- 参数用 schema 生成中文摘要（`city=北京`），原始 JSON 放折叠区；
- 结果区 `max-height` + `overflow:auto`，默认展示前 6 行，超出折叠；
- 同名并行调用各自一张卡，按 `tool_call_id` 配对；
- 工具图标映射：`get_city_weather`→云、`web_search`→地球、`bash`→终端、`read/write/edit`→文件、`ls/find/grep`→文件夹/放大镜。

### 7.3 专用渲染（天气是最典型的例子）

`get_city_weather` 返回的是 wttr.in 的一行文本，直接展示既不好看也不易读。建议：

1. 工具层返回结构化 `details`（`AgentToolResult(content=..., details={...})`），或后端在 `tool_end` 里按工具名解析；
2. 卡片渲染：城市 + 天气图标 + 温度 + 湿度 + 风速；
3. **语义问题**：工具描述是"查询指定城市的实时天气"，参数只有 `city`。用户问"北京明天的天气怎么样"时，模型很可能拿"实时"数据回答"明天"，产生事实错误。建议要么加 `date` 参数（wttr.in 支持 `?format` 的预报接口），要么把描述改为"仅实时天气"，并在系统提示里要求模型说明数据时间范围。
